\noindent
\textbf{Problem Statement}

\vspace{0.3cm}

\noindent
Haskell Language Server (HLS) currently supports \textit{Goto Definition} only for
functions defined within a user’s project. This project extends the feature to
external dependencies, allowing developers to navigate directly to the
implementation of library functions from their IDE. By indexing \texttt{.hie}
files generated by GHC using tools such as \texttt{hiedb}, HLS can locate and
open source definitions from third-party libraries.

\section{The Project}
\subsection{Objective}

\textcolor{magenta}{\textit{What :}} Goto dependency is a feature provided by language servers that improves the user's context on imported symbols. Triggering this on a symbol allows users to view the signature and the underlying implementation of a function they are importing. This helps them understand the abstracted components used within a code block.
\vspace{0.6em}

\textcolor{magenta}{\textit{Why : }} In larger codebases, developers often work with many abstracted symbols that originate from third-party libraries. The current workflow typically involves searching for the corresponding library, locating the symbol manually, and then accessing its implementation. This interrupts the development flow and requires developers to leave their IDE.
\vspace{0.6em}

\textcolor{magenta}{\textit{Limitation :  }} Currently, haskell-language-server provides goto definition functionality for local projects, i.e., when the imported symbols are present within the project folder. However, for symbols provided by third-party libraries, or symbols whose actual source code does not exist within the project workspace, there is currently no support for this feature.
\vspace{0.6em}

\textcolor{magenta}{\textit{Goal :  }} The objective of this project is to extend the existing goto definition functionality to support third-party dependencies. This would allow developers to navigate directly to the implementation of imported symbols from external libraries within their IDE, without needing to manually search for the source code online.

\subsection{Existing Work}
This project was previously attempted in \textcolor{magenta}{PR \#}\pull{3749}. Much of the structural groundwork has already been established there, and this implementation will serve as the base for this project, with further improvements built on top of it.This section outlines the approach taken in that PR.
\vspace{0.6em}

\textcolor{magenta}{HIE :  } When GHC compiles Haskell projects it uses the source files and generates .hi file and object files. Optionally HIE (Haskell information exchange) files are also generated. These contain rich metadata like full typed syntax tree, name bindingss and references, source locations and most importantly original source code of the module embedded as a ByteString. These files are used to implement goto dependency defination.
\vspace{0.6em}

\textcolor{magenta}{Setup :  } HIE files are not generated by default during compilation, passing `-fwrite-ide-info` flag during compilation generates them and stores the resulting files inside cabal package store at a predictable location. extraCompilationArtifacts  constant inside cabal's source governs this predictable location. using the above flag and constant makes sure that HIE files are always generated and ready to be used by HLS.
\vspace{0.6em}

\textcolor{magenta}{HieDb :  }
HLS maintains a SQLite database called HieDb that acts as an index over compiled Haskell modules. It stores metadata extracted from HIE files. HLS uses this database as a fast lookup mechanism when resolving symbol locations, avoiding the need to parse raw HIE files for every query.

\vspace{0.6em}
Most importantly, HieDb stores the path to the original source file i.e for project modules this points to an existing .hs file. For dependency modules, this path is missing because only the HIE file exists in the Cabal store and no corresponding source file is available in the workspace. we builds on this infrastructure by intercepting the point where HLS falls back to HieDb for symbol resolution and generating a source file at that moment.This metadata allows HLS to map a symbol reference directly to its declaration location, making it possible to implement navigation features such as goto definition.

\vspace{0.6em}
\textcolor{magenta}{Mechanism :  }
We can implements goto dependency definition through a pipeline of four coordinated steps.

\begin{enumerate}[label=\textcolor{magenta}{\arabic*.}]
    \item During HLS startup, a new background task called indexDependencyHieFiles performs a breadth-first traversal of the transitive dependency graph, discovers all HIE files in the Cabal store for the current project's dependencies, and registers them in HieDb with a FakeFile marker — indicating the HIE file is known but no source file has been written yet.
    \item when the user triggers goto definition on a dependency symbol, HLS queries HieDb and finds the module's HIE file path.
    \item A new function called lookupMod reads that HIE file from disk, extracts the hie\_hs\_src field containing the original source code, writes it to a deterministic path inside the project root, upgrades the HieDb row from FakeFile to RealFile, and returns the URI of the newly written file to the editor.
    \item when the editor opens this file, HLS detects via getSourceFileOrigin that it is a dependency file and serves hover information and further goto definition requests directly from HieDb, bypassing the normal compilation pipeline entirely.
\end{enumerate}
